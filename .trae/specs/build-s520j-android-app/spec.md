# S520J Android 原生 APP 实现 Spec

## Why

项目目录目前只有两份 V1.0 需求文档（《前端外观设计需求文档》《S520J Android 技术实现需求文档》），没有任何代码、构建环境或网页版原型源码。而技术文档要求"第一阶段即生成可安装 APK、每阶段真机验收后打 Git tag"。因此需要一份可执行的分阶段计划，把"界面复刻 + 双人权限边界 + 全云同步"落成可安装 APK。

## What Changes

- 新建 Android 原生工程：Kotlin + Jetpack Compose + Material 3 自定义主题，minSdk 26，内容区最大宽度 430dp 居中。
- 一次性自举**免管理员命令行构建工具链**（便携 JDK 17 + Android SDK cmdline-tools），每阶段产出 `dist/S520J-<tag>-debug.apk`，用户手动安装真机验收。
- 阶段 1–7 使用 **Room + Fake Repository 的本地 Mock 数据**跑通全部界面与交互；阶段 8 起接入腾讯云开发 CloudBase（云函数 + 云数据库 + 云存储）。
- 实现核心能力：一键注册（昵称 + 8 位账号 ID + 自设恢复码）、共同空间绑定状态机、可见范围两档、内容 CRUD、回收站 30 天、冻结归档、照片上传、通知中心、备份导出。
- 阶段 8 前不做真实推送、不做本地通知、不做免打扰、不做端到端加密。

## Impact

- Affected specs：新建能力域 —— 设计系统、主导航、账号与恢复码、共同空间绑定、内容模块 CRUD、数据同步、媒体、回收站/归档、通知中心、备份导出、构建交付。
- Affected code（均为新建）：
  - `app/` Android 应用（`ui/`、`domain/`、`data/local`、`data/remote`）
  - `backend/cloudbase/` 云函数与数据库初始化脚本（阶段 8 起）
  - `scripts/build_apk.ps1` 构建脚本
  - `dist/` APK 产物
  - `.trae/specs/build-s520j-android-app/` 本文档集

## 文档冲突裁决

两份文档存在不一致，按以下规则裁决（已与用户确认）：

| 冲突点 | 前端外观文档 | 技术实现文档 | 裁决 |
| --- | --- | --- | --- |
| 账号体系 | 昵称 + 邮箱 + 密码 | 昵称 + 系统生成 8 位账号 ID + 自设恢复码 | **昵称 + 用户手动设置账号 ID + 自设密码**（用户确认私人使用，账号可手动设置；账号 ID 规则 8–20 位字母数字，去空格去前后缀后 uppercase 存储，唯一性校验；「恢复码」UI 层全部更名为「密码」，内部实现仍保留恢复码/哈希命名） |
| 可见范围档位 | 仅自己 / 双方 / 指定授权（三档） | 仅自己 / 共同可见（两档，最终确认摘要明确"仅两种"） | **两档**；"指定授权"V1 不做 |
| 视觉/配色/圆角/布局/导航样式 | 有完整规范 | 仅要求"沿用网页版" | **按前端文档** |
| 通知 | 未涉及 | 无系统推送、无本地通知、无免打扰 | **按技术文档** |

补充结论：

- **网页版原型源码不在项目内**，因此"沿用网页版视觉"退化为"以《前端外观设计需求文档》的色值/圆角/结构为唯一视觉基准"。
- 冲突时一律以技术文档第 19 章「最终确认摘要」为最终裁决。

## ADDED Requirements

### Requirement: 分阶段可安装 APK 交付

系统 SHALL 在环境自举完成后，为每个开发阶段构建出一个可直接安装的 APK，产物命名包含阶段 tag，并同步记录构建信息。

#### Scenario: 阶段构建成功

- **WHEN** 执行 `scripts/build_apk.ps1 -Tag v0.1.0-stage1`
- **THEN** `dist/` 下生成 `S520J-v0.1.0-stage1-debug.apk` 与 `build-info.txt`
- **AND** APK 可在真机手动安装并正常启动

#### Scenario: 首次环境缺失

- **WHEN** 机器上不存在 JDK / Android SDK
- **THEN** 先执行一次性工具链自举任务，成功后阶段构建才可运行
- **AND** 自举过程不需要管理员权限、不改动系统环境变量以外的既有配置

### Requirement: 设计系统单一来源

系统 SHALL 把《前端外观设计需求文档》§2.1 的色值、圆角、字体规则定义为一套 Compose 设计 token，所有页面只引用 token，不硬编码颜色与圆角。

#### Scenario: 配色一致

- **WHEN** 渲染任意主页面
- **THEN** 页面背景为 `#F8F6EE`、卡片为 `#FFFEFA`、主色为 `#7D9676`、主要文字为 `#344033`
- **AND** 卡片圆角、间距、阴影在四个主页面保持一致

#### Scenario: 字体大小可调

- **WHEN** 用户在「我们 → 应用设置」调整字体大小
- **THEN** 全应用文字按统一缩放系数变化，不出现布局溢出

### Requirement: 四主导航固定

系统 SHALL 提供四个固定主页面路由 `/heart`、`/gallery`、`/tacit`、`/us`，底部导航固定于屏幕底部、暖白半透明、适配安全区，选中态为鼠尾草绿、未选中态为灰绿色。

#### Scenario: 页面切换

- **WHEN** 用户点击底部导航任一项
- **THEN** 切换到对应主页面且选中态更新，页面保留各自滚动位置

#### Scenario: 新增按钮分布

- **WHEN** 浏览任一主页面
- **THEN** 仅「拾光」显示右下角悬浮加号，其余三页不显示悬浮加号，新增入口位于模块内部

### Requirement: 账号与恢复码

系统 SHALL 提供一键注册：输入昵称 → 生成唯一 8 位字母数字账号 ID → 用户自设 8–32 位字母数字（区分大小写）恢复码 → 直接进入登录态。登录方式为「账号 ID + 恢复码」。恢复码在服务端（Mock 阶段为本地 PBKDF2 模拟）仅存加盐哈希。

#### Scenario: 注册成功

- **WHEN** 用户填写昵称并设置符合规则的恢复码
- **THEN** 生成 8 位账号 ID，账号进入登录态，恢复码以哈希形式持久化

#### Scenario: 恢复码非法

- **WHEN** 恢复码长度不在 8–32 位或含非字母数字字符
- **THEN** 明确提示具体校验失败原因，不进入下一步

#### Scenario: 换机恢复

- **WHEN** 新设备输入账号 ID + 正确恢复码
- **THEN** 自动恢复该账号的云端共同内容与个人内容

#### Scenario: 恢复码无法自助找回

- **WHEN** 用户忘记恢复码且无已登录设备
- **THEN** APP 明确提示无法自助找回，不提供任何查看恢复码入口或后门

### Requirement: 共同空间绑定状态机

系统 SHALL 实现共同空间绑定状态机，状态包含：未绑定、已生成邀请、等待对方加入、绑定申请中、已绑定、绑定失败、冻结归档。一个空间最多两名成员，双方账号不合并。

#### Scenario: 创建并绑定

- **WHEN** A 创建空间并生成绑定码，B 输入绑定码，双方各确认一次
- **THEN** 状态迁移至「已绑定」，共同内容对双方可见

#### Scenario: 解绑冻结

- **WHEN** 任一方发起解绑且另一方确认
- **THEN** 空间进入「冻结归档」，双方可查看与导出、不可编辑
- **AND** 重新绑定后解冻，历史共同内容保留

#### Scenario: 绑定失败

- **WHEN** 绑定码过期、错误或空间已满
- **THEN** 状态为「绑定失败」并给出可重试提示

### Requirement: 可见范围与权限边界

系统 SHALL 为每条内容记录 `visibility ∈ {private, couple}`，默认 `private`；照片与附件继承所属记录的可见范围，不单独设置。

#### Scenario: 私人内容隔离

- **WHEN** A 创建一条 `private` 记录
- **THEN** B 无法看到，也无法申请查看
- **AND** 服务端对每条记录校验 `space_id`、`owner_id`、`visibility`，前端状态不作为权限依据

#### Scenario: 共同内容协作

- **WHEN** 记录为 `couple`
- **THEN** 双方均可查看、编辑、删除，不区分创建者

### Requirement: 本地缓存与增量同步

系统 SHALL 以云端为权威数据源，本地 Room 保存缓存、缩略图索引与离线 outbox；同步触发时机为打开 APP、切回前台、网络恢复、手动同步。同步流程为先推 outbox 再拉增量。

#### Scenario: 离线新增后自动同步

- **WHEN** 离线状态下新增/编辑/删除内容，随后网络恢复
- **THEN** outbox 中的操作按序上传，再拉取服务端增量
- **AND** 同步失败保留 outbox 并提供重试入口

#### Scenario: 冲突处理

- **WHEN** 双方对同一记录产生不可合并的并发修改
- **THEN** 可自动合并的字段合并；不可合并时提示用户选择保留版本
- **AND** 离线删除优先，共同内容进回收站，另一方修改保留为冲突快照（保留 30 天）

### Requirement: 内容模块 CRUD 一致性

系统 SHALL 对所有可管理模块提供统一交互：进入模块 → 列表 → 新增 → 填写 → 上传照片（按内容类型决定是否显示）→ 选择可见范围 → 保存；点击已有内容进入详情 → 编辑 → 删除（二次确认）；并提供搜索、空状态与独立滚动。

#### Scenario: 拾光四模块独立管理

- **WHEN** 点击「共同照片 / 一起做过的菜 / 一起去过的店 / 收藏的瞬间」任一入口
- **THEN** 进入该模块独立内容管理页，而非仅展示统计数字

#### Scenario: 默契八模块独立管理

- **WHEN** 点击八个圆形图标入口中任一项
- **THEN** 进入该模块独立管理页，主页仅展示随选中切换的少量最新记录预览

#### Scenario: 相处之道双方确认

- **WHEN** 一方新增相处约定
- **THEN** 仅双方均确认后才标记为"共同认可"

### Requirement: 共同日历

系统 SHALL 在「心动」页提供完整月份日历：星期标题、完整日期网格、当前日期高亮、有事项日期标记、日期可选、前后月切换、返回今天；下方列出所选日期的待办、重要时间、纪念日、共同计划。

#### Scenario: 选择日期

- **WHEN** 用户点击某日期
- **THEN** 下方列表切换为该日期对应事项，且可新增/编辑/删除事项

### Requirement: 回收站、冻结归档与彻底删除

系统 SHALL 将共同内容删除置入回收站并保留 30 天，任一方可恢复，彻底删除需双方确认；冻结归档中的共同内容不受 30 天自动清理影响。

#### Scenario: 回收站恢复

- **WHEN** 一方在 30 天内对回收站内容点击恢复
- **THEN** 内容回到原模块且双方可见性不变

#### Scenario: 彻底删除

- **WHEN** 一方发起彻底删除
- **THEN** 记录 `purge_requested_by`，待另一方确认后才真正删除

### Requirement: 媒体处理

系统 SHALL 支持多图上传、客户端压缩、断点续传；上传成功后本地保留缩略图，原图按需下载；V1 不支持视频。

#### Scenario: 断点续传

- **WHEN** 上传过程中网络中断
- **THEN** 重新联网后从已上传分片继续，不重复上传已完成分片

#### Scenario: 原图按需下载

- **WHEN** 用户在照片墙点击某张照片查看大图
- **THEN** 通过服务端签发的预签名 URL 下载原图，签发前校验记录权限

### Requirement: 通知中心

系统 SHALL 仅提供 APP 内通知中心，包含所有互动、任务、心愿、日历与系统通知，支持已读/未读；不接入系统推送、不使用本地通知、不提供免打扰。

#### Scenario: 对方离线互动

- **WHEN** 一方发送「碰碰你」而对方离线
- **THEN** 该互动保存为未读消息，对方下次打开 APP 同步后可见

### Requirement: 备份与导出

系统 SHALL 支持手动备份、恢复、导出与清理，导出格式为 JSON + 图片 ZIP 且不加密，导出与备份不需要对方授权，文件可由用户保存到本地或系统文件选择器位置。

#### Scenario: 导出内容完整

- **WHEN** 用户执行导出
- **THEN** 产物包含个人内容、共同内容、照片缩略图/原图索引、设置与回收站

### Requirement: 阶段门禁与全量回归

项目 SHALL 以「阶段」为唯一推进单位，每个阶段必须完整走完「编码 → 阶段自检 → 出包 → 实机验证 → 问题修复 → 全量回归 → 再次验证 → 通过打 tag」的闭环，且任何环节未完成都不得进入下一阶段。

#### Scenario: 计划包含时间节点与实机测试脚本

- **WHEN** 用户阅读 `tasks.md`
- **THEN** 每个阶段都标注「进入条件 / 参考工期 / 计划完成日 / 退出条件」四项时间节点
- **AND** 每个阶段都附一组可逐条执行的实机测试步骤（操作 + 预期结果）

#### Scenario: 阶段编码完成后暂停

- **WHEN** 某阶段的全部子任务编码完成
- **THEN** 必须先做该阶段代码审查与关键路径自测，并构建出该阶段 APK
- **AND** 随后立即暂停开发，向用户提交 APK 路径与该阶段验收清单，等待实机测试反馈

#### Scenario: 反馈问题后必须全量回归

- **WHEN** 用户反馈任意问题或测试结果
- **THEN** 先定位并修复该问题，再对**整个 APP 的全部代码**重新做完整审查、回归测试与功能验证（不得只验证改动点）
- **AND** 全量回归确认无问题后，才可再次发起实机验证请求

#### Scenario: 未通过不得推进

- **WHEN** 阶段尚未获得用户实机验证通过
- **THEN** 不得开始下一阶段的编码工作
- **AND** 不得把「编译通过」当作「验证通过」

#### Scenario: 通过后留痕

- **WHEN** 用户确认某阶段实机验证通过
- **THEN** 在 `tasks.md` 与 `checklist.md` 勾选对应项，并打该阶段 Git tag

### Requirement: TDD 代码生成策略

所有业务逻辑代码 SHALL 采用测试驱动开发（红-绿-重构）：先写一个失败的测试并确认其因功能缺失而失败，再写最少量实现使其通过，最后在绿灯状态下重构。

#### Scenario: 新功能按 TDD 实现

- **WHEN** 新增一个业务行为
- **THEN** 先提交能描述该行为且失败的测试，确认失败原因正确后再写实现
- **AND** 实现只满足该测试所需，不添加未被测试覆盖的功能

#### Scenario: 缺陷修复按 TDD 实现

- **WHEN** 修复一个已反馈的缺陷
- **THEN** 先写一个能复现该缺陷的失败测试，再修复代码使测试转绿，该测试作为防回归证据

#### Scenario: 阶段门禁包含测试全绿

- **WHEN** 某阶段准备出包
- **THEN** `gradlew testDebugUnitTest` 必须全绿且无失败无警告
- **AND** 仅配置与样式类改动（Gradle/清单/资源 XML、纯文案与配色 token、图标资源）可豁免 TDD

### Requirement: 关于 S520J 只读

系统 SHALL 在「我们」页提供固定名称「关于 S520J」的只读模块，展示版本号、版本更新日期、作者 LKS、帮助与反馈，不提供任何编辑或删除入口。

#### Scenario: 只读校验

- **WHEN** 用户进入「关于 S520J」
- **THEN** 页面不出现编辑、删除控件

#### Scenario: 标题规范

- **WHEN** 浏览「我们」页
- **THEN** 不出现「空间与隐私」作为页面标题或独立大区块标题
